# 飞泰 CTP 脚本联机验收记录

测试日期：2026-10-16（Asia/Shanghai）。通过 Axile 0.19.1 REST API 操控账户“宏源测试”（ID 4），使用数据库中已有凭据；没有直接建立 CTP SDK 下单通道。

结论：基础开平撤、重复目标、统计、阈值及本地非法输入已取得联机证据；发送后终止发现残留风险，尚不满足全量验收。各项以以下实际批次结果为准。

## 环境与边界

- API：`http://127.0.0.1:1419/api/v1`，服务算法 `FT-CTP-SCENARIO`。测试合约以各批次配置为准，默认 T2612、1 手、单笔和总敞口上限各 1 手。
- 账户原有 TL2612 多头 16 手，作为保持原数量的目标保留，不用于构造平昨或资金不足。
- 每批独立保存配置恢复、原生订单、成交、控制事件、产品 ZIP 和 SHA256 清单。柜台拒绝需约定条件与期望错误码，条件不足不判通过。

## 未通过与限制

1. `acceptance-pause-after-send-001`：发送后请求 `cancel_pending`，执行在 13:25:45 被强制终止，事件记录 `forced=true`、`cancel_unconfirmed=true`。重连后发现订单 `20261016:1:-1260828858:2`（CFFEX `1155848`）仍挂起，成交 0。其归属由暂停锚点的 monitor `records` 与原生身份精确对应。已通过 Axile 单笔撤单，13:28:02 查询确认“已撤销”、无剩余挂单；证据在 `results/acceptance-recover-after-pause-001/`。不能把终止受理或 execution TERMINATED 当作撤单完成。
2. graceful 模式复验 `acceptance-pause-after-send-graceful-003` 同样在发送后被强制中断，残留订单 `20261016:1:-1249097758:2`（CFFEX `1213967`），成交 0。已在该批次 `recovery/` 中留存单笔撤单及“已撤销”终态，不能将此模式记为通过。
3. 产品账户按日导出普遍报告 `control_counter_activity_time_unknown`；单执行 ZIP 的缺失另逐项保留。脚本不删除该缺口，因此部分业务 passed 的批次仍退出 2。强制终止批次还缺少最终资产与执行摘要、控制会话未正常结束，按原样记录。累计执行数达到产品账户范围导出上限后，还出现 `EVIDENCE_TOO_MANY_EXECUTIONS`，单执行收集仍逐项保留。
4. 后续等待额度／排队／无活跃任务、定时／补发／重启的每次判定见上表；强制中断后的流控不完整状态没有被脚本重置或掩盖。
5. 非法价格首次因 T2612 行情过期在算法前失败，原始批次保留，002 批次已命中 tick 校验。未知合约首次未兼容目录错误并在会话关闭后未完成残留查询，002 批次修复后通过并恢复连接。
6. `acceptance-pause-quota-002` 未到达指定报单额度锚点，任务在行情准备阶段 FAILED；收尾遇到 terminate 409 竞态，原脚本保留未知且未恢复配置。已逐 execution 确认终态，按 restore.json 恢复，见 manual-restoration.json。源码已修复该收尾竞态。
7. 资金不足、市场状态拒绝、真实平昨持仓、部分成交、同步原生失败及飞泰柜台对照，未由本轮条件完整覆盖；不借用 TL2612 持仓、不放宽保护或增加手数制造条件。回归中的替身结果不计入联机通过。

## 本轮脚本修正

- 保留无关持仓的原手数目标，执行前及结束后核对；每个场景开始前再次检查全账户挂单，避免核心执行前清理影响他单。
- 使用真实原生撤单计数名；支持核心直接 NOOP，以最终持仓、无挂单及完整零报撤对账共同证明幂等。
- 兼容当前合约目录返回的空结果错误，查询失败后只恢复连接以核对残留，不重试委托。
- 等待额度直接进入风控，只接受 place_order 的账户每分钟零额度锚点，不把查询节流算作报单等待；排队优先观察首次 QUEUED；本地重启可用监听进程 PID 与创建时间佐证。
- 活跃任务从账户 dashboard 的运行／排队槽位判断，避免把独立账户操作或历史 incomplete 流控上下文当作活跃交易任务。
