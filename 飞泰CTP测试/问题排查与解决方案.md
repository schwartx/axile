## #108：终止清理被同一个终止信号打断

### 已查明的代码链

1. `ExecutionSession.handle_termination_checkpoint()` 在 cancel_pending 模式先调用 `_cancel_pending_orders_before_termination()`。
2. 挂单查询经过 `CTPExecutor._query_connected()`、`_call_trader_request()`；ReqQry* 在原生发送前调用 `_catalog_checkpoint()`。
3. `_catalog_checkpoint()` 看见 active runtime 已终止，调用 `runtime.handle_termination_checkpoint()`，抛出 ExecutionTerminated。查询尚未到原生 API。
4. session 捕获一般查询异常后返回空 failed 列表，无法据此区分“没有挂单”与“查询未完成”。
5. 即使已经知道订单身份，原生 `cancel_order_ctp` 需要等待 `ctp_td_global` 的 1500ms 间隔时，`AccountControlGuard._wait_for_quota()` 仍调用普通终止检查点，风险撤单再次被打断。

不包含飞泰算法的探针结果：

```json
{"query_native_calls":0,"cancel_native_calls":0,"cancel_failed_order_ids":[]}
{"cancel_native_calls":0,"exception":"ExecutionTerminated"}
```

联机服务日志在 13:25:40.519 记录了 `terminate 查询挂单失败: execution terminated, mode=cancel_pending`，与机制一致。

### 测试算法的贡献及剩余边界

测试算法当前一般 Exception 分支会捕获 ExecutionTerminated，finally 再尝试撤单、等待终态、查询成交和资产。撤单被上述门禁阻断后，它可能等待 5 秒；manager 的终止宽限也为 5 秒，因而强制退出。graceful 也有这一放大路径。

所以“清理请求被核心阻断”已独立复现；“最终为何恰好用满宽限”还包含测试算法收尾耗时，不能全部归为核心死锁。两笔真实残留已逐笔撤销，未继续发起联机委托复现。

### 方案

- 增加有界、按 execution/symbol 隔离的终止清理作用域，显式允许既有风险撤单及必要的只读查询完成。保留原有账户额度、共享节流、连接校验与审计；不把整个 guard 关闭，也不允许作用域内发新单。
- CTP query 门禁与流控等待都要识别清理作用域；只改其中一处不能解决问题。清理仍受独立超时、会话断线和硬终止约束。
- 首次观察到终止即记录 ACK，再记录清理阶段。查询失败应传播 query_complete=false / cancel_unconfirmed，而不是仅返回空 failed 列表。
- 将测试算法的终止异常单独处理并在有界收尾后继续向上抛出，避免转成普通 FAILED；非必要的证据补收放到父进程终止后完成。
- 强制退出前保存已经知道的原生订单身份和清理结果。恢复后逐笔核对，不能一键清理无关订单。

### 修复验收

真实 CTP session + guard + Mock SDK：立即终止、共享间隔等待后终止、查询失败、同步撤单失败、迟到回报和双 symbol 并行均覆盖；新单始终被阻止，清理请求按额度最多提交一次；实际未确认时保留具体订单和 unknown。不能只把宽限从 5 秒加大。

## #109：完整性标记与真正的额度恢复缺口

### 已查明

`recover_sessions()` 将上次未关闭的 active 会话标为 incomplete；monitor 对当前 control_date 聚合任一受影响的 incomplete 会话。因此同日新会话正常结束、服务重启，也不会抹掉旧缺口。既有 `test_crash_preserves_last_known_value_and_restart_marks_confirmed_history_incomplete` 明确验证这一行为。

更重要的是：计数增量通常在请求结束时经 `flush_account_control_records()` 刷盘。worker 被杀时，尚未刷盘的本地放行记录会丢失。`build_account_control_guard()` 仅加载已持久化基线，没有依据历史 incomplete 限制新委托。

内存 SQLite 探针：日限额 1；旧 guard 放行一次、不刷盘，模拟进程丢失；recover 后创建新 guard，还能再放行一次。新基线为 0，新 guard 自己的 monitor_incomplete 为 false，总本地放行为 2。这里只复现本地额度决策，未真实报单。

### 方案

- 短期：当前额度窗口存在无法恢复的计数缺口时，对新增风险委托采取明确的保护决策，同时保留风险撤单和必要查询。不能仅在监控 API 标 incomplete，而执行决策仍使用可能偏低的基线。
- 长期：在原生发送前完成可去重的持久化额度预留/操作日志，或采用具有等价崩溃一致性的父进程持久化协议。明确“放行、同步拒绝、柜台受理”计数口径，按唯一操作标识重放，不能重复累计。
- UI/API 分开表达历史日计数完整性、当前连接、当前运行状态和采样时效；返回受影响日期/实例及恢复条件。保留历史缺口，不能用 reset 清零。

### 修复验收

覆盖“放行后发送前崩溃”“原生受理后刷盘前崩溃”“提交成功但响应丢失”、同日重启、跨日、重复刷盘。限额 1 时不能出现两次新增委托放行；风险撤单仍可完成；历史缺口不能被静默标完整。

## #110：负查询为何影响共享会话

### 已查明

`InstrumentCatalog._load()` 对空结果先抛 CATALOG.NOT_FOUND，但捕获各来源异常后只保留文字，最终重新抛出默认 CATALOG.UNAVAILABLE。探针在纯内存空来源上复现了分类丢失。

组合函数通过 `context.get_quote()` 触发该异常，`calculate_portfolio_target()` 将其变成 ok=false 的 PortfolioFunctionResult。`WorkerBackendManager.calculate_portfolio()` 对任意 ok=false 主动 drop_account；注释和既有 `test_calculate_portfolio_drops_worker_after_script_failure` 都确认这是失败隔离策略。因此本次会话关闭有明确软件路径，并不需要假设柜台刚好断线。

### 方案与取舍

- 保留所有查询来源的结构化 cause：全部是 NOT_FOUND 才返回 NOT_FOUND；存在超时/会话失效则分别保留。不要把多个失败统一降成不可用文字。
- 优先增加/复用 instrument-catalog 服务的显式只读精确查询能力，用于元数据探测。负查询不必借道任意 Python 组合函数，也不必丢弃健康交易 worker。
- 对任意用户 Python 失败仍保留 fail-closed 隔离。仅凭 error_type=CatalogError 就取消 drop 并不充分，因为用户代码可能在抛错前已修改进程状态。
- 如需保留组合计算会话，应先具备可验证的只读上下文或独立计算隔离；连接变化中注明“组合函数失败导致主动回收”，不要只留下笼统 503。

### 修复验收

分别验证 NOT_FOUND、多个来源混合失败、目录管道 EOF、原生断线、纯查询失败和任意 Python 修改状态后失败；健康负查询不中断交易会话，真正会话失效仍正确回收。

## #111：行情时效与不必要的规划依赖

### 已查明与未查明

CTPAccountConfig.quote_max_age_seconds 默认 5 秒，同时检查交易所事件时间与本地接收时间。联机记录有 T2612 约 31.9 秒旧的事件，以及 rb2701 事件与接收相差约 47.6 秒的帧。这些超过阈值，按现有规则拒绝符合设计。

当前 `_on_quote()` 已有乱序时间保护，不能没有证据就声称“旧 tick 覆盖新 tick”。交易前置推送稀疏、MD 积压/恢复、原生时间来源等仍需逐 tick 记录，现有摘要不足以唯一归因。

另一个机制已复现：`ExecutionEngine._plan_target_volumes_for_symbols()` 先对全 symbols 调用阻塞行情，再 calculate_target_sizing，最后才判定 NOOP。即使 lots 目标为 0、实际持仓为 0、只是 last_target 带入的旧合约，它的旧行情也能让另一个有效合约在定量前超时。探针记录 blocking_quotes=[T2612, rb2701]，sizing_calls=0。

### 方案

- lots 模式先基于可靠持仓完成精确定量，识别真实 NOOP，再决定哪些品种需要阻塞盘口。权重定量确实依赖价格的路径继续获取有效行情；真实下单仍在原生发送前校验新鲜双边盘口。
- 规划失败按 symbol 留存原因，避免一个无需交易的零目标合约阻断其他品种。不能用旧价格替代真实下单行情。
- 增加有界的每合约接收/有效/拒绝计数、最后事件时间、接收时间、订阅 ACK 和拒绝原因采样，必要时保留最近 N 帧时间证据。用这些证据区分前置延迟、本地积压与时间规范化。
- 在明确的失联/订阅失效条件下执行有界恢复；不关闭 freshness，不直接把 5 秒调大来掩盖问题。

### 修复验收

新鲜活跃合约 + 零目标无仓旧合约可以规划；真实需要交易的旧行情仍被阻止；权重模式缺价、乱序 tick、稀疏同价行情、重连订阅分别验证。上游延迟的最终归因仍需补录，不把该部分记成已解决。

## #112：只读资产被误记执行，以及覆盖口径

### 已查明

`_handle_get_account_assets()` 使用 `request.execution_id or request.request_id` 准备执行器；`_prepare_executor()` 调用 `build_account_control_guard(account, execution_id)`，没有传 context_kind/source，默认值是 execution/algorithm。于是没有交易 intent 的资产刷新也会形成交易类型控制上下文。

只读查询本地数据库得到当天聚合：27 个 execution intent；101 个没有 intent、却被标为 execution/algorithm 的控制上下文。没有依据这些数量推测 101 次交易，它们恰是需要区分的账户操作。

导出 `_select_execution()` 对 execution/未知历史上下文的默认上限为 100。错分类的只读上下文会占这个预算，解释了交易批次远少于 100 时为什么整日导出已经超限。上限本身属于正常资源保护。

另有独立的覆盖口径：日期选择对所有重叠计数桶附加 counter_bucket_context_time_assumed；`_coverage()` 只要看到这一来源就添加 control_counter_activity_time_unknown，使总体 coverage=incomplete。同一份材料的控制探针只增加这个 selection reason，就从 available 降为 incomplete。计数桶确实没有逐笔时间，不能简单删掉事实缺口。

### 方案

- 在请求准备链显式传递 context_kind/source。独立资产刷新使用 account_operation + account_assets；真正 execution 内的资产快照保持原 execution 关联。其他只读命令逐项核对，不能按 UUID 外观猜类型。
- 历史数据只在有明确请求关联证据时修正类型。不能把“没有 intent”一律当作账户操作，历史 intent 丢失的真实执行仍需保留未知。
- 区分“材料齐备”“日期选择精度”“计数逐笔时间证据”。已有精确执行证据时，不用计数桶发现来源笼统污染整个执行材料结论；counter-only 及无法与事件对账的桶仍明确列时间未知。
- 增加有界 execution_ids 清单或小时级窗口选择，方便同一天拆分取证。保留账户所有权校验、只读事务、行数/大小/时间预算、脱敏和 manifest；不直接调大所有上限。

### 修复验收

大量资产刷新不增加交易执行集合；真实执行仍受 100 上限保护；账户操作留在独立材料集合。精确事件+桶、counter-only、跨日期执行、缺 intent 历史、超过一天资源预算、不同账户 ID 混入请求分别验证。
