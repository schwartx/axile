# 日志读取 Python / Rust 性能验收（2026-10-27）

正式实现仍保留 Python。验收要求是内存、CPU 消耗、实际耗时都显著优于原 Python；代码量不参与判定。最初共享定义候选版因内存更高被撤回。后续隔离实验已经消除这项劣势，但原始小负载的普通读取、证据收集只省少量内存，因此暂不将它判为全面通过。

本页保留迁移实验的历史结果。后续已经提交的 Python 时间显示、正文复用和预算检查优化，见[Python 热点记录](Python日志热点优化-20261027.md)。

下面是已经撤回的共享定义初版，保留原始测量记录：

| 场景 | Python CPU ms | Rust CPU ms | Python 耗时 ms | Rust 耗时 ms | Python 峰值 MiB | Rust 峰值 MiB |
|---|---:|---:|---:|---:|---:|---:|
| 读取原始文件 | 112.70 | 53.29 | 112.93 | 54.05 | 120.70 | 136.33 |
| 读取 gzip | 111.12 | 55.02 | 111.28 | 55.08 | 120.84 | 136.12 |
| 读取并渲染时间线 | 710.36 | 307.93 | 712.28 | 308.10 | 123.45 | 126.53 |
| 读取并渲染过程树 | 707.76 | 314.91 | 708.39 | 315.37 | 123.81 | 125.56 |
| 收集日志证据 | 715.59 | 145.68 | 716.09 | 145.79 | 116.67 | 129.27 |

数值为各自五次独立进程的中位数，Python / Rust 按轮次交替执行。原始文件读取的峰值内存增加 12.9%，gzip 增加 12.6%，证据收集增加 10.8%；这三项的五次范围均完全高于 Python。时间线和过程树的内存也没有下降。

同一份冻结数据含 6,098 条记录、原始 JSONL、gzip、嵌套过程、类型化参数、旧版字典日志和重复分片；证据收集匹配 4,613 条。五个场景的全部输出 SHA256 与原 Python 冻结结果一致。文件缓存已预热，工作阶段包含读取、解压、解码及所需展示或收集，不包含导入和结果哈希。CPU 是工作阶段的进程 user + system CPU 时间；内存是整个进程在工作完成时的峰值 RSS，包含 Python 和导入。两种实现使用同一解释器、依赖及当时的原生二进制。

设备为 Apple M1 Max、macOS 27 ARM64、Python 3.12.12；测试时区为 UTC。此结果只代表该固定离线负载，不代表生产交易性能。

最初 Rust 版读取原始文件的峰值约 225.69 MiB。共享优化将它降至约 136.33 MiB，仍高于本次同批 Python 的 120.70 MiB。优化恢复了模板、上下文和字段的共享，去重保存同一记录的引用；剩余开销包括 Rust 记录、排序数据与返回 Python 对象的交叠。因此没有继续保留该迁移。

原始证据保存在本地 `dist/log-reader-benchmark-20261027/`（实验产物不纳入版本控制）：

- `python.json`、`rust.json`：最初各五次测量；脚本和数据冻结不覆盖。
- `resource-comparison-shared.json`：共享优化候选版与原 Python 的五次交替比较，包含 CPU、耗时、内存及全部样本。
- `benchmark_resources.py`：复用冻结 worker，只在其四个计时边界采集 CPU，未在工作期间启用 profiler。
- `rust-shared-candidate-source/`、`rust-shared-candidate.abi3.so`、`shared-record-source-checkpoint.json`：实际测量候选版的源码、二进制及哈希。
- `python-restored.json`：恢复 Python 后的最终复测；与 Rust 比较的上述原始数据分别保留。

冻结主脚本：`scripts/benchmark_log_files.py`，SHA256 `7e52e5b514971662e904dca2373547e363e767df02fb6fc22627e8590e793409`。数据 SHA256 `34cc69033b8f2bd46ea93a1d7612e5b50bb81416c3935f595b57bee53b50da73`。

最终 Python 版本保留轮转、重启后丢弃计数恢复、展开预算、逐条脱敏和绝对时间排序修复；同时保留归属过滤后再展开正文、正文拼接前的字节限制和越界时间错误处理。Rust 写日志队列不在此次回退范围。


## 内存救援实验

所有候选版只在忽略的 `dist/log-reader-benchmark-20261027/memory-rescue/` 中研究，未替换正式 Python 读取器或正式 `_core` 二进制。原始冻结脚本、Python 基线源码和 6,098 条数据均未改变；Python 基线没有预加载 Rust 扩展。继续按完整进程峰值 RSS 判断内存，未将它换成工作增量或对象图大小。

V4 将 Rust 记录改为共享不可变定义，逐批生成最终 Python 字典并及时释放临时记录；普通字典只共享键，不共享可变的 args、事件或过程字典。渲染路径仅按需展开正文。证据收集的去重表在返回对象后复用同一个 Python 记录，释放私有字段快照；普通游标默认仍保留独立快照。预算、归属过滤、完整重复比较、冲突、丢弃计数和取消检查均保留。

V4 完整原生扩展，五次交替独立进程的中位数：

| 场景 | Python CPU ms | Rust CPU ms | Python 耗时 ms | Rust 耗时 ms | Python 峰值 MiB | Rust 峰值 MiB | 内存减少 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 读取原始文件 | 113.30 | 47.39 | 113.76 | 47.47 | 120.84 | 118.64 | 1.82% |
| 读取 gzip | 112.89 | 47.96 | 113.15 | 48.03 | 120.92 | 118.58 | 1.94% |
| 时间线 | 722.17 | 292.60 | 726.01 | 293.01 | 123.59 | 116.67 | 5.60% |
| 过程树 | 728.64 | 302.04 | 732.65 | 302.62 | 123.77 | 117.09 | 5.39% |
| 证据收集 | 712.78 | 125.75 | 713.54 | 125.89 | 116.64 | 115.97 | 0.58% |

五个场景的全部输出哈希与冻结 Python 完全一致。各自五轮 RSS 范围均分离，已经测到稳定的降低；但 0.58%–1.94% 的小幅降低不足以据此宣布满足用户的“每项显著更好”。182 项定向 Python 检查通过，包含原有读取、证据、计数、写日志及额外普通字典语义和边界对照；这不等于完整回归或新 wheel 的交付验收。

V3 另用原生成器将每运行事件数从 2,000 增为 10,000，补充测得 30,098 条记录时，原始读取峰值 178.89 → 156.25 MiB（减少 12.66%），证据收集 159.13 → 147.53 MiB（减少 7.29%）。这说明记录越多，减少对象复制的收益越明显；它不是原始五类负载的替代验收，也不是 V4 的测量结果。

完整扩展仍有固定加载成本。隔离的约 0.83 MiB 只读二进制，单次诊断可再省约 1.5–2 MiB；完整二进制增加第二个只注册读取器的初始化入口没有得到相同收益。只读二进制缺少存储和写入入口，不能直接替换正式 `_core`；因此尚未增加第二套产品打包流程。

可复现证据：

- `memory-rescue/resources-v3.json`、`resources-v4.json`：各自五类原始负载、全部五轮样本、CPU、耗时、RSS、范围、源码和二进制哈希。
- `memory-rescue/resources-v3-scale5.json`、`scale5-provenance.json`：大负载两类五轮比较及数据来源。
- `memory-rescue/source-v3-archive/`、`source-v4/`、`prototype-native-v3.abi3.so`、`prototype-native-v4.abi3.so`：保留候选源码和对应产物。
- `memory-rescue/quick-lite.json`、`quick-dual.json`：轻量入口和双初始化入口的单次诊断，不作正式验收。

V4 完整候选原生 SHA256：`e1acdf9848fac89272e082c9e2107fb0cd2c098da2d4f1c4594a0342a48137ea`。测量时正式 `_core` 为原写日志扩展，SHA256：`9f7b8c79ac6036d907d0cd377f08aced849ba8dfd027540f28d771b44c0fc62a`。


### 合并轻量二进制与共享缓存

V4-lite 同时启用 V4 共享记录缓存和仅注册读取入口的编译特征。只读二进制大小 889,040 bytes；这是避免加载完整存储扩展的实验，不是可直接交付的 `_core` 替代品。

| 场景 | Python CPU ms | Rust CPU ms | Python 耗时 ms | Rust 耗时 ms | Python 峰值 MiB | Rust 峰值 MiB | 内存减少 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 读取原始文件 | 111.88 | 47.58 | 112.17 | 47.69 | 120.70 | 116.47 | 3.51% |
| 读取 gzip | 113.28 | 48.97 | 113.53 | 49.22 | 120.67 | 116.38 | 3.56% |
| 时间线 | 708.42 | 292.72 | 709.72 | 293.15 | 123.38 | 115.03 | 6.76% |
| 过程树 | 723.19 | 306.42 | 725.18 | 307.90 | 123.77 | 115.20 | 6.92% |
| 证据收集 | 717.97 | 124.50 | 718.66 | 124.62 | 116.52 | 114.11 | 2.07% |

仍为同一份原始冻结负载、五轮交替独立进程，全部输出哈希一致，各场景 RSS 范围分离；`memory-rescue/resources-v4-lite.json` 保存全部样本和源码哈希。该候选二进制 SHA256：`38eaa2dc72e9c9af7c9852c19e4dd5912f3ec5e96a216b46669451b5d289733b`。

小负载总 RSS 受共同的 Python 导入与运行时占用影响，但不能据此把验收指标改为扣除导入后的内存；2.07%–3.56% 仍只判为小幅降低。完整存储扩展与轻量读取器若拆成可交付产品，还需要额外构建和 wheel 验证，当前没有引入这项复杂度。

审查另外发现候选版既有兼容边界：证据扫描中的旧版字典日志若把 `run_id` 或 `seq` 写成 list/dict，原生身份字符串化会接受它们，而 Python 去重键会拒绝不可哈希值。没有为本次研究将它静默判为等价；候选仍不是完整交付版本。


V4-lite 的 30,098 条补充负载同样执行五轮交替进程：

| 场景 | Python CPU ms | Rust CPU ms | Python 耗时 ms | Rust 耗时 ms | Python 峰值 MiB | Rust 峰值 MiB | 内存减少 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 读取原始文件 | 559.26 | 240.73 | 561.93 | 240.92 | 178.64 | 154.17 | 13.70% |
| 证据收集 | 3507.82 | 641.79 | 3536.63 | 642.59 | 158.70 | 142.97 | 9.91% |

完整样本为 `memory-rescue/resources-v4-lite-scale5.json`，各场景的五轮内存范围分离、全部输出哈希相同。V4 完整扩展的 182 项定向测试通过（`tests-v4-cache.log`），新增 20 项共享缓存测试也在 V4-lite 通过（`tests-v4-lite-cache.log`），覆盖重复不收费、数值等价、默认快照隔离、冲突、异常和中断传播。没有运行完整回归、Rust 单元测试或轻量版本的正式 wheel/跨平台交付验收。

研究结论：重复数据复制的问题可以显著改善，最佳隔离原型的大负载内存已省约 10%–14%；原始小负载普通读取和证据收集只省约 2%–3.6%，没有达到“所有场景每项都显著更好”的保守验收口径。正式实现继续使用 Python，候选源码、原生二进制和原始测量保留供后续复用。本轮未提交、推送或部署，也未替换正式原生库。
