# 成本品种页批量读取实验

分支 `perf/cost-read-path`，从 main `5eeae32` 新建独立 worktree。原 DuckDB 分支保持不变；本阶段不迁移存储、不引入 DuckDB/Arrow、不改接口及前端、不合并或部署。

## 发现与改动

当前品种页已经使用 SQLAlchemy Core 和 SQL 聚合，没有通过 Python 解码完整成交 payload；不能把这一条路径描述为 ORM 大对象问题。但每个品种单独查询数量、最后时间、汇总和手续费，20 行页面共 86 次 SELECT。

本改动先确定当前页品种，再按页批量执行聚合和费用查询，完整请求降为 8 次 SELECT。Python 仅组装当前页及分币种费用；SQL 聚合表达式、null/零/数量未知和手续费口径沿用原实现，不新增缓存、表或冻结汇总。本阶段仍在 SQLite 内提取 side/quantity JSON 字段，没有宣称消解 JSON。

## 三轮实际 HTTP 对照

使用上一实验明确标记的 100000 笔、100 品种合成冻结数据，SHA256 `26220e0fd5024f6b94b7bb4070488e5413d13a36f83430184577888f13b3b096`。这是规模案例，不能称真实 CHEN 历史；完整 CHEN 原副本与旧写入器冻结参考未修改。本阶段不单独补做普通小数精度验收，遵循先验证方案的范围。

完整 FastAPI 应用组装，真实 Uvicorn/loopback HTTP，两个源码目录使用相同 Python 环境，独立进程与数据库副本，轮换顺序。关闭交易/调度生命周期并禁止服务端出站连接。客户端独立进程，服务端 RSS 包括应用、SQLite 和 Python 的全部开销，没有 DuckDB/Arrow。六类请求为品种排序、成本排序、买入、卖出、文字筛选和第二页，各三遍。

“启动＋请求”为完整应用启动加 18 次 HTTP 请求耗时，不含独立客户端初始化、比较和请求间准备；“热请求”为后两遍共 12 次。稳定 RSS 在仍监听时采样一秒；峰值为系统 ru_maxrss。热系统文件缓存，未强制 GC。首轮 baseline 早期有相关短测试并行，其他轮没有；报告三轮中位数，后两轮速度差同向，不宣称严格独占机器的基准。

| 实现 | 启动＋18 次请求（秒） | 12 次热请求（秒） | 峰值 MiB | 稳定 MiB |
|---|---:|---:|---:|---:|
| main | 10.335 | 6.038 | 202.00 | 201.95 |
| 按页批量读取 | 9.374 | 5.408 | 201.84 | 201.80 |

全部 18 次响应在两组各三轮的完整 JSON 数值、字段、排序和分页游标一致，未排除游标或做精度舍入。源库哈希和运行期间两份实现源码哈希保持不变。两轮之后 baseline 的 18 次请求分别 9.475、9.432 秒，candidate 分别 8.511、8.490 秒。

结论：启动＋请求约减少 9%，热请求约减少 10%；稳定内存差约 0.16 MiB，按基本持平处理。批量化有小幅速度收益，但不是主要内存问题的解决方案。没有继续扩大修改，也没有自动合并 main；下一步需讨论是否保留这个小优化，或转向明确类型事实列/冻结汇总，以消除扫描与 JSON 提取。

已有分析测试 24 项通过；新增多品种测试覆盖当前页数量、查询上限、逐品种摘要对照、真实零、缺失数量、null、不同币种手续费、第二页和空筛选。发行层现有 161 项测试通过，改动文件 Ruff 格式/静态检查及复杂度检查通过。接口形状及前端代码不变，本阶段未另开浏览器。
