# 文件日志

Python 保留 Loguru 和标准库 logging 的现有调用方式，经一个薄 sink 提交给当前进程的 Rust 日志队列。Rust 原生入口直接提交到同一队列。主进程和账户 worker 各自创建写线程、文件和运行标识，不共享活动文件。

文件读取、解压、协议校验、模板展开、时间归并、过程树和计数汇总由 Python 处理，共享模板和上下文定义。2026-10-27 的 Rust 读取迁移仍未达到内存、CPU 和耗时都显著更好的要求；后续候选已降低内存，但小负载收益有限，正式实现继续保留 Python。对照见[性能记录](../review/日志读取性能对比-20261027.md)。

CLI 批量显示复用已经展开的正文，时间前缀在单次调用中只缓存当前绝对秒；外部可变记录仍按当前字段渲染。证据导出按展开后的 UTF-8 字节精确计费，每条记录及最多 64 KiB 或剩余额度检查预算、取消和超时。优化与边界验证见[Python 热点记录](../review/Python日志热点优化-20261027.md)。

队列默认容纳 4096 条事件，机会式取批，每批最多 256 条。满队列丢弃新事件并计数；调用方不等待队列空位或落盘确认。日志内部错误不控制订单、交易或执行状态。编码、复制参数和内存队列仍有 CPU 开销，不能理解为零延迟或硬实时保证。

控制台输出与 gzip 压缩各使用独立后台线程。慢终端不阻塞文件写线程；后台压缩失败保留原文件。日志模块不使用 SQLite，也不复用业务数据库队列。

后台消费者固定绑定各自的运行标识，关闭超时后仍存活的旧线程不会读取新运行的队列，也不会把旧归档错误记入新运行。线程创建失败不阻止业务启动，文件日志和其他消费者继续工作；初始化故障恢复后，相同配置可以重试。

## 计数

`axile.server.core.log_config.logging_stats()` 读取当前进程计数，不经过日志队列。原生入口为 `_core.logging_stats()`，返回 JSON 字符串。

- `accepted_total`：已接受到队列的日志事件。
- `written_total`：已写入文件的日志事件，不代表每条已完成持久化同步。
- `dropped_total`：明确主动丢弃的事件数。
- `dropped_by_reason`：队列满、无法编码或写入器不可用的原因分项，合计为 `dropped_total`。
- `write_errors_total`：文件写入或同步错误次数。
- `unconfirmed_total`：写入故障涉及、最终存储结果未知的事件数，不能当成精确丢失数。可能与 `written_total` 重叠。
- `console_dropped_total`：控制台队列溢出或输出失败，不代表对应文件事件丢失。
- `archive_errors_total`：压缩任务无法安排或压缩失败，原始日志保留。

正常级别过滤不计丢弃，多行正文和堆栈按一条事件计数。写线程周期保存累计快照，恢复后报告丢弃摘要。跨分片汇总时，每个 `run_id` 只取最新快照，不能把累计值重复相加。磁盘不可用期间，内存中的即时计数可能比历史文件中的最后快照更新。

丢弃摘要通过普通 `E` 事件保存和输出，使用相同的时间与序号；正常退出也会保存最后的摘要。内部统计快照默认不显示在时间线或过程树中，通过 `--stats` 查看。摘要和快照不计入调用方事件的接受、写入计数。

写线程退出时只将尚未写出快照的丢弃增量留给后续运行；停止后新增的拒绝也会保留。恢复时吸收一次，旧线程延迟退出仍能转交，已写出的旧快照不会重复计数。

## 文件协议

每行是一个完整的 UTF-8 JSON 数组：

```text
["H",1,{"run_id":"运行标识","time_base":"UTC绝对时间","time_unit":"us"}]
["T",template_id,level,message_template,field_names,metadata]
["C",context_id,values]
["S",span_id,parent_span_id,name,context_id,start_us]
["E",seq,time_us,template_id,context_id,span_id,args]
```

模板、上下文和必要祖先过程由写线程在首次引用之前写出，定义和事件不会分开争抢队列。字段按位置对应，保留 JSON 值的类型。`context_id=0` 表示空上下文，`span_id=null` 表示无过程归属。

`seq` 在同一次运行内递增，轮转不重置；显示时间是写出口的非递减接收时间，不等于跨线程的真实发生顺序。每个分片可独立解码，跨进程按执行 ID 等上下文关联，查看端提供稳定归并。

现有 Loguru 消息通常已经展开，使用 `{message}` 模板承接；需要参数级去重时可显式绑定 `_log_template` 和 `_log_args`。模板只支持命名字段与转义花括号，不执行属性、下标访问或格式规格。未用于文案的参数仍会显示。

Python 可以用 `axile.common.logging.log_span()` 记录有身份的嵌套过程。它保留原业务异常及取消信号。Rust 公共业务入口记录自身过程，复用调用边界传入的执行上下文。过程开始、事件、结束分别保存；缺少起止或父过程时明确显示，不推断成功。

## 轮转与查看

默认按 `1 day` 时长或 128 MiB 轮转，以先达到者为准。一个不可拆分的事件及其必需定义可以使分片略超上限。`axile_log_rotation` 沿用 Loguru 字符串规则，包括 `00:00`、`daily`、`monthly`、`Monday at 12:00`、`1 h`、微秒时长、组合时长和文件大小；也保留 `100 bytes` 写法。时长从运行起点计，日历规则使用机器本地时间；`1 month` 是固定时长，`monthly` 是月历边界。时间规则仍受默认大小上限约束；大小规则仍受默认 UTC 天界约束。原生 API 不传规则时保持既有 UTC 周期边界。文件名含 UTC 起始时间、运行标识和分片编号，重启新建文件，不覆盖旧日志。

已关闭分片以仅当前用户可读写的权限创建 gzip 文件，校验能完整还原后才移除原件。不新增自动清理或保留期限，磁盘容量仍需运维管理。

```bash
axile logs logs/axile-*.jsonl
axile logs logs/axile-*.jsonl.gz --tree
axile logs logs/axile-*.jsonl logs/axile-*.jsonl.gz --stats
```

时间线和实时输出使用同一文本渲染规则。新旧日志按绝对时间归并，保留原始时区文本，缺失时间的历史记录稳定排在前面。查看器拒绝定义冲突、未定义事件引用、参数数量错误、不完整尾行和中间损坏。证据导出分别限制解压扫描量和定义展开后的记录量，先检查事件归属、去重和剩余预算再拼接正文，逐条脱敏写出；显式报告损坏和已知日志缺口，同时可以读取旧版字典 JSONL。

过程树中时间相同的同级过程按首次观察到的关联事件序号排序，不使用过程编号代替事件顺序。本实现为写出的每条 `E` 连续分配序号；查看器在合并、去重后报告同一运行输入范围内的序号缺口，标注材料不完整，同时保留已观察到的过程结果。单个较晚分片不因未输入较早分片而报中间缺口；没有运行清单时，无法确认运行首尾材料完整。

正常退出限时排空。CLI 既有的立即退出信号处理保持不变；强杀、进程崩溃或断电可能丢失最后一批日志和尚未保存的计数，不能承诺精确统计这些损失。
