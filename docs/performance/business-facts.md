# 执行业务事实的结构化存储

0034 从已发布的 0033 直接迁入最终业务列与明细表。Rust 负责业务存储、迁移和版本化分析发布；Python 负责业务协调。前后端随同一个包发行，升级后同步使用新表结构和接口，不维持旧内部 JSON 的完整形状。

## 事实模型

| 存储 | 业务含义 |
| --- | --- |
| `executerecord` | 原记录身份、执行标识、终态、生命周期状态、原因、耗时及终止证据 |
| `execution_input` | 下单前冻结的业务输入；不再另存相同的审计输入版本 |
| `execution_input_target` | 当前账户目标、上次目标和策略目标三个不同口径；同义别名合并，真实冲突进入审计证据 |
| `execution_input_plan` | 数量与合约单位分别保存；不通过权重、价格或乘数反推缺失值 |
| `execution_input_symbol` | 有序风控品种，保留重复发生和异常原值 |
| `execution_symbol_*` | 品种结论、数量换算依据和首笔行情 |
| `execution_order_*`、`business_trade_*` | 订单与成交发生、原生编号、数值、费用可用性和转换依据 |
| `business_asset_snapshot`、`business_asset_position`、`business_asset_binding` | 资产观测、持仓及观测引用；执行前后属于不同观察时点 |
| `target_weight_snapshot_weight` | 一次目标计算的原始和归一化权重 |
| `execution_extension` 与对象的原生扩展 | 动态配置、`extra`、`memory` 和少量异常审计证据 |

分析直接读取权威业务事实，不再维护 `analysis_source_*`、`replay_observation*` 中间副本。五表模型保存当前账本和可重建的日级成果；成本明细按需读取业务事实。

迁移核对成功后删除 `executerecord.raw_input/raw_result`、`account_asset_snapshot.assets`、`target_weight_snapshot.raw_weights/normalized_weights`。ORM 不提供恢复整份旧 JSON 的隐式属性。

## 精简边界

正常数值直接写业务列。不再保存 `field_metadata`、字段列表、数字表示类别、映射键顺序和逐字段摘要投影路径。整数 `0` 和浮点数 `0.0` 的旧表示不构成业务差别；原生编号 `0` 与字符串 `"0"` 仍是不同编号。

有业务意义的缺失、null、真实零和不可用状态分别保留：例如目标集合、数量计划、资产金额、持仓金额、最终数量与费用。接口以命名的 `availability` 状态和实际数值表达这些含义。异常值保留在稀疏 `audit_evidence` 中，不成为可用业务数值，也不补成零。原生 `extra`、`memory`、规则和换算参考中的 null、零、来源及原始内容继续保留。

订单号和成交号不作为跨记录唯一键。重复订单、成交和持仓观察各自保留；实际数组顺序保留，业务映射不要求旧键顺序。品种映射键与嵌入 `symbol` 各自保留，观察路径采用 RFC 6901 转义。

目标明细直接以 `(input_id, role, map_key)` 为主键，数量计划以 `(input_id, symbol)` 为主键，使用 `WITHOUT ROWID`，删除重复唯一索引和不参与读取的索引。不同业务口径即使数值偶然相等也不合并。真实不同的历史输入、审计目标和资产时点各自保留。

## 时间存储

0034 的绝对时刻列统一使用有符号 INTEGER Unix 微秒，列名以 `_us` 结尾，基准为 UTC 1970-01-01。执行耗时也使用整数微秒。Python 使用 int、Rust 使用 i64；毫秒和秒来源在存储边界按声明单位换算，不根据位数猜测。

历史无时区的标量时间按执行迁移机器的本地时区解释，包含该日期的夏令时规则；显式时区按原偏移转换。必需的非法时间使整个迁移回滚；可选渠道时间沿现有稀疏异常证据表达未知，不补当前时间。JSON 列原样保留，不遍历或改写其内部时间。业务日期、交易日、风控桶身份和已有幂等标识保持原语义。

分析、增量游标、时间范围及排序直接使用整数；按上海日期或账户时区计算日界后再查询 UTC 半开区间。接口在出口转换为明确带时区的 UTC ISO 文本，已有毫秒数值接口保留原单位。正常时间不长期保留一份重复文本副本。

新库和 `0033→0034` 使用同一标量转换规则；同号的旧开发期 0034 结构明确拒绝，不在启动时自动转换。降级恢复旧字段类型和等价 UTC 时刻；逐字恢复迁移前原文依靠升级前整库备份。原生事实能力号为 41，防止误加载旧时间格式的扩展。

## 事务与完整性

1. 下单前，worker 同步提交冻结输入和可用的执行前资产，成功后才允许继续下单。输入、目标和规则附件引用同一个已提交输入身份。
2. worker 在回传执行结果前提交执行后资产和结构化结果。终态尚未存在时，观测由输入拥有；终态可通过绑定复用相同观测，不重复保存持仓。
3. 父进程在同一事务中结算任务终态和通知，并使账户分析版本失效。`facts_complete` 在明细完成后置为真，事务内外读取均不会把尚未完成的事实当作完整结果。
4. 新事实图构建时，子行不逐条更新账户分析版本。终态写入使其统一失效。已完成图的后续追加、修改和删除仍会更新相关账户分析版本，回滚同时回滚版本变化。

已有冻结输入重放必须语义一致，终态不能覆盖下单前输入。引用会校验账户、执行和观测时点。集合计数与发生序号用于完整性检查；明确记录为新版的事实缺少明细时抛错，不静默回退到旧 JSON、空集合或零。

## 接口与审计

`GET /api/v1/account/execute_records/{account_id}` 返回分页摘要；列表不读取完整输入、资产、订单和成交。

`GET /api/v1/account/execute_records/{account_id}/{record_id}` 返回头字段及显式 `input`、`result` 业务视图。前端选中或展开后加载详情，跨账户记录返回不存在。上次目标、资产总额和活动页成本使用窄查询。

输入、目标、规则和前后资产附件使用 `schema_version=3`，通过 `business_facts_ref` 引用不可变输入或资产身份。新目标视图返回三个业务口径、数量计划、换算参数和必要的异常证据。0034 迁移的历史目标及规则附件按原字段集合投影，保留 `account_target` 等别名；别名复用规范事实，真正冲突的旧目标保留在审计证据中。

0034 不保存 EXECUTION_SUMMARY 或结果扩展 reconciliation。详情、证据导出和迁移校验共用 Rust 计算函数，从冻结事实临时组装摘要和对账；未知观测保持未知。Python 只负责调用。worker 回传前提交结果事实，父进程另行结算任务终态和通知。冻结通知 outbox 保留发送当时的正文。

0034 无清理执行历史接口及隐藏标记，全部已结算执行参与历史和绩效分析；worker 暂存结果仍待父进程结算后可见。删除账户时物理删除其执行事实。

## 升级与回退

前后端、公共核心和私有发行层使用匹配版本。升级前停止旧写入进程。空库直接创建最终 `0034` 结构，已有数据库仅支持已发布 `0033` 升级到 `0034`。`0001`—`0032` 在数据库变更前报错，提示先安装 Axile `v0.23.1` 并完成升级到 `0033`，再安装本版本。历史逐版本迁移链和开发期中间结构不提供升级或降级兼容；同号的开发期 `0034` 通过结构校验拒绝。

跨入 0034 前，迁移取得写锁，通过 SQLite Backup API 在数据库同目录生成 `<数据库名>.before-0034-<进程号>-<序号>.bak`，包含已提交的 WAL 数据，权限沿用原库，已有备份不覆盖。迁移回执返回 `backup` 路径；备份失败则不开始转换。备份、升级需要额外磁盘空间。

0034 不再保留 `_futures_close_policy_backup`、`axile_0013_error_backup`、`axile_0014_market_value_backup`、`axile_0015_tq_market_value_backup`、`axon_0001_error_backup` 五张历史迁移备份表。从 0033 升级到 0034 时在同一事务中删除它们，新建库不创建。已经是 0034 的库正常启动或重复升级不会自动清理，使用下述独立脚本处理。私有错误码补丁仍然生效，但不再支持逐项回退到私有 `base`；公共结构回退到 `0033` 不恢复这些历史备份。需要恢复迁移前原值时使用升级前整库备份。

已经迁到旧版 0034 的库，停止服务后执行 `python scripts/cleanup_0034_migration_backups.py /path/to/axile.db`。脚本独立运行，只依赖 Python 标准库，严格检查版本为 0034；所有删除在一个事务中提交，可重复执行，不修改业务事实或版本号，不自动 VACUUM。

旧版订单跨进程重建可能改变 `update_time`。0034 迁移仅对缺少 `update_timestamp` 和 `extra._update_time_str`、具有有效本地 ISO 时间且其余订单字段完全一致的记录兼容此差异；两份时间及原摘要附件 ID、类型、版本、创建时间和订单路径保存在结果的 `audit_evidence.legacy_order_update_times`，不覆盖结果时间，也不保留重复摘要正文。该证据记录历史差异，不将任一时间认定为交易所原始时间。

摘要缺少完整事实、含其他独立字段或与规范结果冲突时拒绝升级，整笔事务回滚，先核对并修复对应事实再重试。清理摘要不会自动缩小 SQLite 文件；需要回收文件空间时应在离线维护窗口另行执行 VACUUM。降级不会重建已删除的可推导摘要，稀疏订单时间证据随结果保留；存在未结算结果时拒绝降级到 `0033`。

业务转换、逐项证据校验、旧列删除、约束安装和版本写入在同一个事务内完成。任何一步失败，结构、业务数据、旧缓存和版本号一起回滚。历史执行、资产、目标、审计、通知和原有身份保留；显式 `null` 与字段缺失分别记录，读取和降级时保持区别。缓存不参与业务证据转换。

旧绩效缓存统一清空，运行中的领取状态重置；账户重新排队，按现行业务事实重算。迁移直接创建五表分析结构，运行时不解析旧缓存 JSON。首次重算完成前暂时没有可展示的绩效版本。

降级到 0033 前检查待完成输入和资产是否有可恢复的承接记录或附件；无法无损承接时拒绝降级，保持原库不变。检查通过才重建旧版可消费的业务文档、恢复旧账户主键规则和缓存空表，再移除新表。新绩效缓存丢弃，不要求恢复旧缓存；旧字段顺序和数字字面表示不属于回退保证。若选择恢复升级前备份，应停止全部进程并同时处置原库的 WAL/SHM；该备份不包含升级后的新增业务数据，不能用它覆盖仍需保留的新记录。

## 验证与性能

验收范围涵盖真实 `0033` 升级及双链回退、旧版本拒绝、提交前失败、事务回滚、输入和资产归属、集合缺失、原生编号及费用、按需摘要与历史读取、冻结通知、真实本地 Rust 分析、前后端共用场景及实际 wheel。前端交互另行进行可见浏览器验收。

同样本测量见[业务事实存储与服务合成对照](business-facts-measurement.md)。数据库体积和写入退化需要逐项定位；拆表本身不能成为接受退化的理由。合成测量、安装、前端验收、部署和真实渠道执行属于不同验证范围。
