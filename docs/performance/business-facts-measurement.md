# 业务事实存储与服务合成对照

2026-10-21 的同样本复测显示：精简后数据库体积小于原版，列表继续保持轻量；写入比首轮实现改善，仍慢于原版。详情与服务 RSS 也仍高于原版，不能据此宣称整体性能问题已解决。

## 样本与完整性

原版为 PR 原头 `59dac8bedc72debf4fc253e3ab9183135f01eb3e`，精简版测量检查点为 `7f330749a2a8b3b5789f695504267ae40b68ada0`；之后只整理文档和提交历史，运行时代码及资源由源码/产物哈希再次核对。

同一份冻结成功合成样本含 200 次执行、每次 12 个品种，共 4,800 个订单、9,600 笔成交和 2,400 条执行后持仓。样本 SHA256 为 `32dae82fe61688f6b1b6ed1bdc2cddf08b3b7f84664e640ba6134c3a5936fef1`，未额外嵌入 `result.inputs`。两臂顺序运行，SQLite WAL、`synchronous=FULL`，保留实际写入器与事务边界；建库、迁移、样本构造和事后校验不计时。

业务结果、审计附件、审计事件和九类分析事实的哈希全部一致。对照不要求旧键顺序、整数/浮点字面表示和旧内部 JSON 外形；集合 null/空/缺失、原生证据、重复发生和不同业务目标仍参与核对。原版审计写入器额外注入的空 `sizing_context={}` 不包含参数，与未提供上下文按同一业务口径比较；非空参数及真实目标差别仍会失败。独立 golden 测试另核对命名可用性状态和原生编号类型，避免只依赖归一化比较。

| 终态保存 P50 / P95，ms | 6.833 / 8.878 | 29.602 / 33.548 | P50 4.33× |

数据库净分配是相对空库的已分配页增量，WAL 是文件占用峰值，二者都不是累计磁盘写入量。

首轮结构化实现曾占用 31,674,368 净分配字节，生命周期 P50 为 79.380 ms。该版本 `field_metadata` 占 7,689,800 字节，正常执行保存两份输入，目标明细 16,800 行，重复目标索引约 2.73 MB。精简版删除通用 JSON 还原元数据；200 次执行仅有 200 个冻结输入、7,200 行三口径目标，并改用没有重复唯一索引的复合主键。

首轮每条子行都推进账户分析版本，200 次执行将 `source_version` 推到 52,800。精简后为 1,200；原版为 400。新图在同一事务内完成后统一失效，已完成图后续修改仍失效。另删除新执行逐表清空不存在明细的操作。下单前、执行后观测仍分别提交，不为压缩事务次数牺牲业务证据。

这些结果证明元数据、重复输入和失效放大可以消除；写入仍为原版约 2.56 倍，尚未完成剩余耗时的逐 SQL 归因，不能将差距解释为拆表的必然成本。首轮历史数字与本轮使用相同样本，但耗时来自不同测量窗口，只作改进方向对照。

## HTTP 与 RSS

完整 FastAPI 应用在独立进程导入，关闭交易、渠道、调度和分析生命周期。每臂 GET 重复 5 次、终态写入 3 次、并发读写 2 轮；计时与 RSS 使用不同新进程和数据库副本。共同头部、完整 input/result、上次目标及每个进程新增的 5 条提交均完成核对。

| 场景，P50 ms | 原版 | 精简版 |
| --- | ---: | ---: |
| 账户列表 | 2.344 | 2.283 |
| 执行历史列表 | 9.936 | 5.168 |
| 完整详情 | 3.709 | 10.917 |
| 上次目标 | 1.338 | 1.665 |
| 仅终态写入 | 8.264 | 22.897 |
| 并发中的完整详情 | 11.250 | 44.119 |
| 并发中的终态写入 | 14.045 | 46.300 |

历史列表响应从 660,629 降至 34,682 字节（−94.75%）；完整详情从 32,647 增至 40,176 字节，包含明确的业务可用性状态。

服务 RSS 采样峰值为 **186.016 → 206.000 MiB**。两臂均无活跃 Rust 或其他子进程，不能推断实际分析期间的内存。RSS 含完整应用导入和未计时的证据复读；5 ms 采样可能漏掉短峰，共享页可能重复计数。单轮小样本 GET 不能推断生产尾延迟。

## 复现与边界

使用 `scripts/benchmark_business_fact_storage.py run --scope lifecycle` 分别运行旧源码和本分支，再将两份数据库交给 `scripts/benchmark_business_fact_service.py`。两臂使用相同 harness 与独立的 `scripts/business_facts_contract.py`，报告分别冻结脚本、oracle、源码、样本与数据库哈希。

存储检查点的源码身份哈希：原版 `1a1f4a08a9b300f310f3115c3645445912d73f82b76a36b49c997371b4032b40`，精简版 `88f23126bc421082b3c74933d905703d3970002e20aefc9d8ced955e60b06cfd`。

本机原始证据归档的 `formal/` 保存两臂 JSON、数据库、比较报告；`service/final.json/` 保存 timing/RSS 子进程报告。前一轮未通过审计口径核对的尝试独立保留，不计入本页结果。

本测量不包含迁移耗时、真实柜台、生产部署或跨平台压力。实际 macOS arm64 wheel、双链迁移与可见浏览器验收另行核对，不以本页的性能结果替代。
